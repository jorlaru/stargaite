# Phase 7 design: the guided console

Status: draft for the owner, revision 3, after two review rounds (each: four Fable reviewers and four Fable verifiers; 63 then 61 findings kept, one refuted) and the owner's answers to eleven questions (2026-11-18). It builds on the code at `b781172` and on `docs/design/phase-6.md` (cited as "phase-6 §M"). Its inputs are the owner's live check of phase 6 on a clean Debian 13 machine (2026-11-18), run as an external reader following the README on GitHub ("the live check"), and the conversation that followed, in which the owner chose the console's shape from mockups. Code is cited as `path:line` of `b781172`. C59a, the skeleton, is built and measured (§9, §12); the later steps are not, and what they claim about a library comes from a probe build (§12), not from use.

## 1. Why

The live check reached a first answer with `./setup.sh`, then judged it, in the owner's words: "esto no es usable. Así de claro". The assistant works; using it does not. A line-by-line question script cannot be made pleasant, so the findings are resolved by a different tool, not patched one by one. The owner asked for a console as usable as interactive terminal tools like Claude Code's, designed from the reader's experience.

## 2. Goals, non-goals, anti-goals

**The rule this phase adds:**

> **The console always guides.** A person never needs to know a command, a name or a file. They open it, see what exists and what is missing, pick what to do from a list, and are led through short steps, each choice picked from a list whenever the answer exists or a provider lists it. Free text is typed only for a new name or a value. Every task ends with its result and returns to the same question.

Goals, at the end of phase 7:

- A first run goes from a clean machine to a first answer in one guided flow with a step bar (§4.1), including optional fallback models.
- Every later change is a guided task from one home menu (§4.2, §4.3), which also suggests what is missing.
- A reader can give an alias models from different providers, in order, as fallbacks; cap spending on everything, on an alias, or on one app or agent (its key); add several providers in one go, each key tried for free before it is written.
- Models are listed sorted and grouped by vendor and family, chat models only unless asked.
- Phase 6's subcommands and the new tasks that touch the host also run from flags, with or without a terminal (§4.4, OPS-2, OPS-11).
- **The code is easy to change: a task is one plain Go function that reads as its steps, top to bottom (§5). The owner stated this as vital, on par with the screen.**
- A cancelled paid check stops at the server, not only in the console (§3, owner question 9).
- The README shows the console with images rendered from its own tests.

Non-goals: managing a remote StargAIte from another machine; running on macOS or Windows (the console compiles there, as `make ci` builds every package for `darwin`, `Makefile:9`, but runs on Linux, as phase 6); a web UI; new proxy capabilities beyond the one CLI flag of §3 (Paid cancel); translating the console (English, PUB-8); flags for tasks the `stargaite` CLI already does without questions (§4.4); stepping back one question inside a task (§3 Esc).

Anti-goals (a failure even if it works):

- A console that holds rules the proxy already holds (validation, prices, budget reach, defaults): two places to keep in step.
- A new door into the proxy: no admin port published, no Docker socket in a container.
- New dependencies in the proxy binary or its image.
- A provider or telemetry credential on screen, in argv, in a log, in the scrollback, or in any file but `.env`. The client key is the one secret shown, once, by design (§3).
- A paid call without the reader's explicit order (an Enter on a screen that states its count, or naming the task in flags mode, as phase 6), any retry of one, or one that a cancel leaves running at the server.
- Code a newcomer cannot follow: logic split across layers, flows hidden in callbacks.

| TUI library | Bubble Tea v2 only, pinned (`charm.land/bubbletea/v2` v2.1.2); width, cutting and any styling with its own `x/ansi`. | Screen mode | Inline: one long-lived program for the session; each change prints one permanent transcript line before it is made; the live view holds only the current step. ### 4.1 First run

"Progress" is the work piece (C59b), with no animation (owner, 2026-11-19); C60 puts it around the readiness wait, the free key check and the model list, so Esc stops them. Three pieces of the list above are not built: `result` (a result is a said line, C61), `table` (C63) and, since C64a, `follow`: See logs' follow is a work piece whose lines are said.

**A task is a plain Go function**, `func(ctx context.Context, u *ui.UI, px *proxy.Proxy, h *host.Host) (string, error)`, read top to bottom. Shared steps are plain functions in `task/` with explicit inputs and outputs, such as `pickModel(ctx, u, px, provider) Target`, each owning its questions as `ui.Question` values; a task's step table is the concatenation of its steps' tables; a nested task runs through `u.Run(sub)`, which swaps the step bar. Loops over items are a `PickMany` followed by `for`, and per-item flags are keyed by item. As built in C60, the alias and provider tasks share their steps as methods on one `run` value (`task/alias.go`): the doors, what the run read (`r.providers`, `r.targets`, `r.models`, filled by `listProviders`, `listTargets` and `listModels`), and what it changed, said on an early end; a step that reads what the run read says so in its comment, the caller gives each shared step its question's ID, flag and step, and each task writes its own step table.

**The UI is one concrete struct**, in a package that does not import Bubble Tea. Each typed method (`Pick`, `PickMany`, `Text`, `Secret`, `Confirm`, `Paid`, `Work`, `Say`, `Show`, `Table`, `Follow`, `Reveal`) does, in order: check the question is in the task's table, take `answers[q.ID]` (from flags or a suggestion's presets), else `front.Ask(ctx, q)`, then `q.Check`. `Reveal` shows the client key: the guided front on the alternate screen until confirmed, the plain front once on standard output. Leaving a task is an error value, `ui.ErrLeave`, returned by any method when the reader presses Esc; a task returns it as is, after saying nothing more. `Front` has two methods, `Ask` and `Show`, and two implementations: `guided` and `plain`. Tests use the UI with an answers map and the plain front, which is flags mode itself. A question a flag answers has the flag's name as its ID, and a per-item flag is `name=VALUE` pairs read through `Question.Item`; a bare value answers only the items that ask the same variable.

**The session and the terminal.** `main` owns the work, not Bubble Tea: one session goroutine (`for { choice := u.Pick(menu); run(choice) }`; since C61 that loop is `task.Home`, which `main`'s session goroutine calls, while `main` still owns the `done` channel, the recover and the signals) with a `done` channel and one `recover` (which maps a panic to exit 1 with one line, for every front); after the program's `Run` returns, `main` cancels the root context and waits for `done`, bounded at 12 s, before exiting or re-execing. One context per task derives from the root; Esc cancels only that one. One signal owner: SIGINT, SIGTERM and SIGHUP cancel the root context. A `go` statement is allowed only in one helper that recovers, checked by the imports test. The root model only renders what it is asked: header, step bar, current piece, last result, and a spinner when no piece is active. As built in C64b: `task.ErrReexec`, an error value as `task.ErrEnd` is, is what the home returns after an Upgrade or Rebuild whose new console was exported; `main` decides on it only after the program has quit (`restartDecision`: within the bound, no signal, no Ctrl-C, no panic, the marker not set) and then calls `syscall.Exec` once; the terminal's pending input is flushed before each guided program starts (`flush_linux.go`, `flush_darwin.go`, an ioctl, not `os/exec`).

**Processes.** `host/exec.go` runs every external command: `exec.CommandContext`, each child in its own session (no controlling terminal) with the git variables of phase-6 §2 on every git call, its process group signalled with SIGINT on cancel and killed after 10 s, phase 6's bounds, and three output modes: *display* (cleaned, with Compose's `.env: line N` errors cut after the line number), *capture* (returned to `proxy/`, never displayed or quoted in an error, even on a decode failure; only the decoded `.error.message` is shown, and for `keys create` or `rotate` a decode failure says the key exists and must be rotated), and *file* (standard output to an `O_EXCL` `0600` file under a `0700` `backups/`, or standard input from a regular file, never a terminal). As built in C64a, the file mode is `host.Backup` (`backup - --json`'s standard output to `backups/<name>.part`, linked to `backups/<name>` once whole; its summary and any error read from standard error, where the CLI writes them) and `host.Restore` (`docker compose run --rm --no-deps -T stargaite restore --yes -`, its standard input the copy, checked a regular file again once open, returning restore's exit code). `host.Backup` returns a bare reason, so each caller composes its own sentence (C64b's Upgrade reuses it). C64b adds `host/git.go` (every git call with the git variables, reads within `h.bound`, the fetch within 20 s, a fast-forward merge only, within 2 minutes, its stop an error value of its own), `host/tls.go` (the host's addresses, the rootless and group checks, the self-signed certificate, the own pair, `tls/` written with its owner and modes, the expiry), `KeepImage`, `ComposeBuild` and `ExportConsole` on the quiet bounded run `up` already used, and, in `host/http.go`, `CheckHTTPS`, the one data-plane check without the provider guard, since it dials this host's own addresses; `host.Restore` now returns restore's decoded answer.

**HTTP with a secret.** `host/http.go` holds one client constructor: transport built from scratch, no proxy from the environment, no redirects followed, keep-alives off, 30 s, a size-capped read, the system roots for providers, and for the data plane a pool holding only `tls/<ca>` with the fixed dial address and server name; verification is never disabled. Three functions: `ListModels`, `TryCompletion` (behind `paid`), `Ready`. C59b lands `ListModels` and readiness; `TryCompletion` lands in C61 with its 30 s timeout, `max_tokens` 256 and its 502 and timeout texts.

**Secret input.** The secret piece renders nothing of the value, not even mask characters; it accepts a terminal paste as one message; it refuses what `setup.sh:139-141` refuses (empty, `'`, a newline, a trailing `\`) before returning.

## 12. Dependency cost (measured 2026-11-18)

A probe console with `charm.land/bubbletea/v2` v2.1.2, `charm.land/bubbles/v2` v2.2.1 and `charm.land/lipgloss/v2` v2.1.1, built with the project's Go image: 3 direct and 17 transitive modules (one, `golang.org/x/sys`, already present), all MIT or BSD; the stripped static binary is 4.2 MB against 1.5 MB for a hello world (+2.7 MB). Risks accepted: frequent releases of a recent major version; `github.com/charmbracelet/ultraviolet` pinned at a pseudo-version. If C59a finds detection at `init` time in a library, it is recorded here as an accepted risk or the writer that does it is dropped. `govulncheck` covers the console; a pinned version moves only for a finding or a needed fix. None of it reaches the proxy binary or its image (§5).

What C59a settled (2026-11-18):
